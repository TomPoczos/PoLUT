# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A uv project that digitizes manufacturer datasheet curves (Kodak, so far) into profile JSON for darktable's native `spektrafilm` module (`src/common/spektra_sim.c`, `src/iop/spektrafilm.c` in a darktable checkout) — the spectral film simulation ported from Andrea Volpato's `spektrafilm` Python project (github.com/andreavolpato/spektrafilm, GPLv3). This is a sibling tool to `../curve_digitizer/`, reusing its PDF vector-extraction engine, but targets a completely different consumer/output format: not `generate_film_looks.py`'s `.cube` LUTs, a fitted multi-layer density-curve model plus spectral data on fixed grids.

darktable's spektrafilm module does not ship any per-film curve data itself — it's loaded at runtime from a "data pack" (`pack.json` + `spectra_lut.f32` + `profiles/*.json`) that lives outside the darktable tree, normally produced from a `spektrafilm` release by `spektrafilm_export_data.py`. This tool produces one additional profile the pack doesn't already have, by digitizing the real datasheet instead of depending on `spektrafilm` upstream ever measuring that stock.

## Commands

```
uv run main.py                          # build every product in main.py's PRODUCTS dict
uv run main.py --only kodak_trix400      # build one (or more) by stock slug
uv run main.py --skip-external-validation  # skip the ~/venv-spektrafilm-dev round-trip check
uv run validate_external.py <profile.json> # run that check standalone against a profile file
```

No test suite, no linter configured — the only "check" is running `main.py` and reviewing the QA images/`fit_report.json` it writes, plus the external validation step. Everything a run produces is written under `outputs/`, organized by taxonomy path (`outputs/<support>/<channel_model>/<type>/<brand>/<stock>/`, e.g. `outputs/film/bw/negative/kodak/kodak_trix400/`, `outputs/paper/bw/kodak/kodak_polymax_fine_art/`) and nowhere else — this tool never writes into a shared directory outside its own project folder (contrast `curve_digitizer/main.py`, which writes into PoLUT's own `film_paper_filter_data/`), and never touches a real darktable `devconfig/spektrafilm/` pack directly; copying a reviewed profile there is a deliberate manual step, not something any script here does.

### Deploying a profile to darktable for real testing

Copy `outputs/.../profile.json` to **both** of these, renamed `<stock>.json`
(e.g. `kodak_trix400tx_d76_9min.json`):
```
~/code/darktable/devconfig/spektrafilm/profiles/<stock>.json
~/code/darktable/devconfig/spektrafilm/packs/<hash>/profiles/<stock>.json   # <hash> varies, ls the packs/ dir
```
The second one is not optional. darktable's `_resolve_pack_dir` (in
`spektrafilm.c`) resolves and loads from the hash-keyed snapshot under
`packs/`, not the top-level `profiles/` dir directly — a profile only
copied to the top-level dir silently won't appear in darktable's film-stock
list at all. Restart darktable after copying either way (no live reload).
The devconfig's own `pack.json` (both the top-level and the hash-keyed
snapshot) also needs `pack_format: 2` for a rebuilt darktable to load
*anything* from the pack at all — check that first if every stock suddenly
vanishes after a darktable rebuild, not just this tool's own profiles.

## Architecture

**Pipeline, per product** (see `products/kodak_trix400tx.py` for the reference implementation): digitize the datasheet's H&D/spectral-sensitivity charts (`digitizer_core.py`) → fit a grain-layer density-curve model to each H&D curve (`density_model.py`) → assemble the pre-collapse source shape and derive the single deployable `profile.json` from it (`spektra_profile.py`) → validate (`spektra_profile.py`'s own structural asserts, plus `validate_external.py`'s in-memory round-trip through the real `spektrafilm` package against the pre-collapse shape, never written to disk itself — see that module's docstring).

- **`digitizer_core.py`** — copied verbatim from `../curve_digitizer/` (its shared, vendor-agnostic PDF vector-extraction engine: `ChartSpec`/`CurveSpec`, the three extraction strategies, axis calibration, RDP simplification, QA overlay rendering). Not modified here and shouldn't need to be — if a real bug is found in it, fix it upstream in `curve_digitizer` and re-copy, since the two tools are meant to share one proven engine, not fork it. Kodak's ~1997-2003-era datasheets (every product so far) use Strategy D (`vector_position`): curves share one ink color and are told apart by position, not color — but *how* varies per chart, confirmed by direct testing, not assumed: most (e.g. every kodak_trix400.py chart) print an inline text label right next to each curve, but at least one (kodak_polymax_fine_art.py's Spectral-Sensitivity Curves panel) instead uses marker glyphs (■/□/○) at the trace endpoints with a separate, ambiguously-positioned legend block — label-position matching against that legend text produced a confirmed, physically-backwards assignment. **Always check the QA overlay before trusting a new chart's curve-to-label assignment — and don't stop at "it looks plausible," verify it numerically or against an independent source, because a wrong assignment can look completely clean.** Three different failure modes have shown up already, all invisible in the raw R²/point-count numbers (every one of them still fit beautifully, R²>0.999, because a WRONG label on a REAL curve is still a real, fittable curve):
  - Small (16-point) leader-line/tick-stub fragments near text labels getting extracted as candidate traces (kodak_trix400.py's D-76 panel) — fixed by raising `min_trace_points` past the fragment size, confirmed via `extract_traces_in_region()` probed directly.
  - Labels in a separate legend block rather than adjacent to their own curve (kodak_polymax_fine_art.py's spectral-sensitivity panel) — fixed by ranking traces by vertical position at a shared wavelength instead of by label proximity.
  - **The hardest one, and the one that actually shipped wrong before being caught**: `kodak_polymax_fine_art.py`'s two multi-grade panels (filterset1/filterset2) have real, clean, single-token inline labels ("#1", "#3", ...) with real leader lines — everything about them *looks* like the normal, reliable case. But all 3 curves per panel sit within a few pixels of each other at every point near where the labels/leader-lines actually are (confirmed by direct probing: interpolated trace positions at several candidate x/y test points were within 1-2px of each other, not a real signal) — so BOTH of `digitizer_core.py`'s matching heuristics (rank-order and fallback distance) silently produced a wrong, self-consistent-looking answer; nothing about the R²/violation counts hinted at it. Only caught because the user cross-checked the actual assignment against the source PDF directly and found 2 of 3 swapped in one panel and all 3 cyclically wrong in the other. Fixed by abandoning automatic label matching entirely for these two panels and assigning by `extract_traces_in_region()`'s own **trace index** instead, with the correct index→grade mapping recorded as a manually-verified constant (`FILTERSET1_TRACE_GRADE_BY_INDEX` etc.) plus a point-count fingerprint asserted at digitize time so future drift (e.g. a `region_bbox` edit that changes which vector objects get picked up) fails loudly instead of silently re-shuffling grades. **Lesson: clean single-token labels with real leader lines are necessary but not sufficient — if multiple curves are genuinely close together anywhere near the label/leader-line region, check actual separation numerically (probe `extract_traces_in_region()`'s trace values at the candidate x/y directly) before trusting either matching heuristic, even when the QA overlay legend renders without any visible red flag.**

- **`kodak_helpers.py`** — Kodak-specific PDF quirks that don't belong in the vendor-agnostic core, ported from `curve_digitizer/kodak_common.py`. Both functions handle the same underlying problem (this era of Kodak sheet draws a tick's minus sign as a vector overline, not a text glyph, so plain text extraction reads negative ticks as unsigned) on the two shapes it shows up in: `overline_negative_calib()` for an axis with one genuinely-unsigned endpoint (negate everything else), `overline_symmetric_calib()` for an axis with real ticks on both sides of a real 0.0 (negate everything past the zero tick). Check for this quirk on every new Kodak-era chart before trusting `fit_axis`'s plain text-based reading of a negative-valued axis.

- **`canonical_grids.py`** — the exact 81-point wavelength (380-780nm/5nm) and 256-point log_exposure (-3..4) grids every profile's spectral/density arrays must be sampled on exactly (darktable's C reader requires an exact length match, no partial/resampled fallback). Reconstructed via `numpy.arange`/`linspace` and confirmed bit-exact against a real pack's own arrays rather than pasted as literals, so there's no transcription risk.

- **`density_model.py`** — fits `D(logE) = Σ amplitudes[i]·Φ((logE-centers[i])/sigmas[i])` (a sum of `n_layers` normal CDFs, `model_type="norm_cdfs"` in the schema) to a digitized H&D curve via `scipy.optimize.curve_fit`. Each layer is meant to represent one grain-speed sub-population (fast/mid/slow); **`sigmas` must stay bounded** (`fit_norm_cdfs`'s own `bounds=`) or the optimizer can converge to a degenerate solution where one layer's center and sigma both blow up proportionally just to mimic a constant offset — same total-curve fit quality (R² unaffected), but not a genuine sub-population, and a bad basis for the native grain model. Confirmed this actually happens without the bound (sigmas ~1e8-1e11 on first attempt); don't remove the bound to "let the optimizer explore more."

  **The fitting target passed in MUST be net density (digitized density minus that curve's own `base_density`), never raw absolute digitized density.** This was a real, shipped bug (2026-08-02): both `products/*.py` originally fit directly against raw digitized H&D values (which include base+fog, since that's what a real chart plots), producing a `density_curves` array that *also* included base+fog baked into its low-exposure asymptote — but the render pipeline adds `base_density` back a second time on top (`compute_density_spectral()` in spektrafilm's Python `develop.py`, and `cmy_to_print_lograw()`/`cmy_to_log_xyz()` in darktable's `spektra_sim.c` — confirmed identical in both, real per-pixel hot-path code, not a peripheral function). Net effect: every rendered density came out too high by roughly the base density, at every exposure level — confirmed as the actual cause of a reported "image renders far too dark, even *more* crushed with the print stage skipped entirely" bug (misleadingly looked like a film/paper exposure-calibration or pairing issue at first; it wasn't — check this class of bug before chasing exposure-anchor theories). Every product's `build()` must subtract `base_density` from the digitized points before calling `dm.fit_norm_cdfs()` — see either product script's own comment at that call site for the pattern. A correctly-fit curve's `density_curves[0]` (canonical grid's lowest exposure) should approach ~0, not the material's own base density; sanity-check that directly on any new profile before trusting it.

- **`spektra_profile.py`** — builds profile JSON as plain dicts/numpy arrays directly against the documented schema, not a parallel dataclass hierarchy (there's no real behavior to reuse, just a JSON shape, so a second class hierarchy would only be something to keep in sync with upstream as it drifts). One file is written to disk per product now (`profile.json`), not two — until darktable's `pack_format` 2 (`~/code/darktable` commit `eedbad83dc`, "support pack v2 files, fix Tri-X column layout to follow upstream spektrafilM"), a second, separately-widened file was required because darktable's C reader *guessed* whether a BW stock's fitted `density_curves_model` outer axis was the development-time family or a channel axis from its row count — wrong on at least one real stock (Kodak Double-X, off by 1.34 density) and the exact bug that hit this project's own Tri-X profiles (named directly in that commit message). Pack format 2 resolves that axis from the profile's own `channel_model` field instead, so the model no longer needs pre-widening — verified both by reading the current C source and against real upstream profiles already in the devconfig pack (`kodak_doublex.json`, a genuine 5-development-time family, ships `density_curves_model.centers` as `(5, 3)` = `(n_dev, n_layers)`, un-widened, under this same pack format). Two builders remain, but only one still gets written to disk:
  - `build_source_profile()` — spektrafilm's own "source profile" shape (what `spektrafilm/data/profiles/*.json` holds, single-channel for BW — `log_sensitivity`/`channel_density` carry exactly ONE column, not three — and can carry a real multi-development-time family: `base_density`/`density_curves` get one column per development time, `density_curves_model.{centers,amplitudes,sigmas}` get one *row* per development time). Kept in memory only now — never written to `outputs/` as its own file — as the input to `collapse_to_darktable_pack()` and to `validate_external.py`'s round-trip, which still needs this exact un-widened shape (see that module's docstring for why that skew is unrelated to today's darktable fix and still stands).
  - `collapse_to_darktable_pack()` — produces the one shape that's actually written to disk as `profile.json` and read by darktable's C loader (`sf_profile_load` in `spektra_sim.c`). Still a port of `spektrafilm_export_data.py`'s own BW collapse/widen block (find it at `~/code/spektrafilm-export-data/spektrafilm_export_data.py`, function `main()`, "stock profiles" section) for the pieces that are still genuinely required: collapses a development-time family to its middle *position* (`idx = (len(times)-1)//2` — order `development_time` ascending so the middle position is the value you actually want as the representative), then widens `log_sensitivity`/`channel_density`/`density_curves` to 3 identical RGB columns and flattens `base_density` to one value per wavelength — all still mandatory, confirmed unconditional in the current C reader regardless of `pack_format` (see `spektra_sim.c`'s `json_read_dmatrix(..., SF_NWL, 3)` calls, untouched by the pack-v2 commit). **No longer widens `density_curves_model`** — that field is written straight through in its real, un-widened `(n_dev, n_layers)` shape now (see above). Accepts `len(development_time) >= 1`, not just a real (`> 1`) family — a print paper commonly has *no* genuine development-time axis to collapse (see the `products/` bullet below) but still needs the same widen-to-3-columns step every profile gets on its non-model fields; `idx` falls out to `0` for the trivial single-value case with no special-casing needed.

  Also home to `validate_source_profile()`/`validate_darktable_pack()` — local structural asserts. These deliberately do **not** mirror `spektrafilm`'s own installed-package validator; see the schema-skew paragraph below for why that validator isn't the right authority for the darktable-facing file.

- **`exposure_calibration.py`** — cross-calibrates a B&W **negative** film's `log_sensitivity` absolute scale against spektrafilm's own internal exposure convention. **Required for every B&W negative film product, not optional.** `black_white_filming_exposure_correction()` (spektrafilm's own reference code) is a hard no-op (`return 1.0`) for `info.type=="negative"` — unlike the print stage, which auto-normalizes around whatever density the film's midgray produces, a negative film's exposure computation has zero safety net, so a source chart's own absolute sensitivity units (e.g. Kodak's "ergs/cm²" spectrograph convention) have to be explicitly shifted onto spektrafilm's own scale or the whole tonal range lands in the wrong part of the density curve. Confirmed as a real, shipped bug (2026-08-02): unshifted, Tri-X 400 put a normal 18%-grey scene at 99.99% up its own density curve (pinned in the flat shoulder) — every rendered image was crushed/flat regardless of print paper, and *worse* in scan-only mode, which is what actually proved the bug was here and not in the print/paper stage. The correction target (`GREY_TARGET_LOG_RAW = 0.743`) isn't arbitrary — it's the empirically-confirmed value 5 independent real shipped profiles across different manufacturers/film types all converge on for a flat 18%-reflectance/D55 input (within 0.03 log10 units of each other), which follows directly from the runtime's own documented contract (`spektrafilm/README.md`: input is scene-referred linear RGB, where a properly-exposed neutral subject renders at ~0.18) — every correctly-calibrated profile has to agree on what "expose a grey card" means, regardless of which film is loaded. See that module's own docstring for the full derivation and which stock types this does/doesn't apply to (paper stocks and B&W *positive*/reversal stocks are different cases, explained there).

- **`validate_external.py`** — round-trips the in-memory pre-collapse source profile (never written to disk as its own file anymore -- see `spektra_profile.py`'s bullet above) through the **real, already-installed** `spektrafilm` package at `~/venv-spektrafilm-dev` (the venv `refresh-spektrafilm-profiles.sh`, in a darktable checkout, already maintains for this exact purpose) via subprocess, rather than adding `spektrafilm` and its full runtime (colour-science, numba, rawpy, exiv2, lensfunpy, PySide6, napari, OpenImageIO...) to this project's own dependencies just to reach one small validation function. `validate_spektrafilm_source_profile()` (dict in, used by `main.py`) writes to a scratch temp file internally and cleans it up; `validate_spektrafilm_source_externally()` (path in) is kept as the standalone CLI entry point (`uv run validate_external.py <profile.json>`) for pointing at an arbitrary file on disk. Probes for the right module path at runtime (see next paragraph) rather than hardcoding one.

- **`products/`** — one module per film or paper *stock family*, following `kodak_trix400.py`'s shape (single-stock: `build()`/`OUT_DIR` at module level) or `kodak_polymax_fine_art.py`'s shape (multi-stock: several closely-related variants sharing one source chart/pipeline, its own `PRODUCTS = {stock_slug: <has .build()/.OUT_DIR>}` dict merged into `main.py`'s). Adding a new single stock: write `products/<new_stock>.py`, register it in `main.py`'s `PRODUCTS` dict. Adding a new family: follow `kodak_polymax_fine_art.py`'s own shape.

  Every real product built so far digitizes fresh from the PDF in this project's own session, with its own QA overlay per curve, full stop — **do not reuse a curve's points from an external file just because it looks plausible and has its own metadata/QA image, even from elsewhere in the PoLUT corpus.** An earlier version of `kodak_polymax_fine_art.py` reused a grade's H&D curve from `consolidated-data/paper/kodak/black-and-white/kodak_polymaxfineartpaper_2005.json`, an earlier PoLUT corpus pass — reasonable-looking (real rendered PDF background, real Kodak figure codes, its own QA overlay), and on inspection it *was* real, not fabricated. The user still pushed back and asked for it to be re-digitized fresh in this project regardless, and that's the right default going forward: independent, in-session verifiability is worth more than saving the (real, but not huge) cost of re-extracting a chart that's already been digitized once elsewhere. `kodak_polymax_fine_art.py`'s current version digitizes all 3 characteristic-curve panels (all 7 grades) fresh, in this project, every run.

  Paper stocks (`kodak_polymax_fine_art.py`) differ from film in a few real ways, not just cosmetically — check that module before assuming film conventions apply:
  - `reference_illuminant` is a tungsten enlarger lamp SPD (`"TH-KG3"`), not `"D55"` — paper is exposed by the enlarger, not daylight. Confirmed against every real paper profile already in the pack.
  - A variable-contrast paper's several curves (different filter/contrast grades) are **not** a `development_time` family, even though they look like one (multiple H&D curves for one product). darktable's `development_time`/`print_development_min` is real minutes, UI-labeled and suffixed as such (`spektra_sim.c`) — a paper's grades typically share one real, fixed development condition and vary by contrast filter instead, a variable the current schema has no field for. Stuffing grade numbers into `development_time` would mislabel them as minutes in the UI. Ship each real grade as its own separate stock instead (real precedent: `kodak_portra_800`/`_push1`/`_push2` already ship as separate stocks for one physical film at different processing) — `kodak_polymax_fine_art.py` ships all 7 real Polymax grades (-1..5) this way, picked up from the paper dropdown directly, closer to how a darkroom printer actually selects a physical filter than morphing one fixed curve via `print_contrast` would be.
  - `log_sensitivity_density_over_min` doesn't have to be `1.0` — that value on film profiles so far is a datasheet-availability coincidence (the criterion the source chart happened to publish), not a hard convention. Pick whichever criterion the actual source chart offers and is real/standard for that material (`kodak_polymax_fine_art.py` used 0.6, the real ISO 6:1993 paper-speed criterion, since its datasheet doesn't publish a 1.0 curve at all).
  - `collapse_to_darktable_pack()`'s `len(development_time) >= 1` acceptance (not just `> 1`) exists specifically so a paper's single-representative-curve-per-grade case still goes through the same widen-to-3-columns step as a real film family.
  - Set a film's `info.target_print` to a real paper stock slug once one exists (`kodak_trix400.py` → `kodak_polymax_fine_art_grade2`, the grade Kodabrome II RC's own datasheet calls "normal contrast") — leaving it `null` isn't neutral, see the darktable-pairing note below.

## Non-obvious behaviors worth knowing before you debug something

**`profile.json` (the darktable-facing shape) fails the installed `spektrafilm` package's own validator — this is expected, and only partially fixed by darktable's pack_format 2.** The schema is presently a moving target across four places that don't fully agree with each other: the local `~/code/spektrafilm` checkout (`main` branch, has `spektrafilm/profiles/io.py`) is *older* in one respect than the installed `~/venv-spektrafilm-dev` package (a `dev`-branch snapshot, module moved to `spektrafilm/data/profiles_loader.py`, and its `_validate_profile` expects a BW stock's `log_sensitivity`/`channel_density` to stay single-column forever — a `channel_model`-derived `n_channels` property, never widened). darktable's `spektra_sim.c` C reader picked up `pack_format` 2 on 2026-08-03 (`~/code/darktable` commit `eedbad83dc`), which fixed the specific ambiguity around `density_curves_model`'s outer axis (see the `spektra_profile.py` bullet above) — but its `log_sensitivity`/`channel_density` reads (`json_read_dmatrix(..., SF_NWL, 3)`) are untouched by that commit and still unconditionally require 3 widened columns, confirmed by grepping `spektra_sim.c`'s git blame (that call site has had exactly one commit, its original introduction) and by real upstream BW profiles already in the devconfig pack (`kodak_doublex.json`/`kodak_2302.json` both ship `log_sensitivity`/`channel_density` 3-wide under this same `pack_format: 2` pack). So this specific skew — widened-for-darktable vs. single-column-for-the-newer-Python-validator — is independent of `pack_format` and still stands; that's *why* `build_source_profile()`'s un-widened shape still exists in memory (for `validate_external.py`) even though it's no longer written to disk as its own file. The darktable-facing file's authority is `spektra_profile.validate_darktable_pack()`, which mirrors the C reader directly. If a future darktable release ever drops the unconditional 3-wide requirement for `log_sensitivity`/`channel_density` too, `collapse_to_darktable_pack()`'s widening of *those* fields could be dropped the same way its `density_curves_model` widening already was — check `spektra_sim.c`'s `json_read_dmatrix` calls for those two fields specifically before assuming it, the same way this note itself was confirmed rather than assumed.

**A film with `target_print: null` doesn't render as "no paper" — it silently picks whatever printing-stage stock sorts first alphabetically.** Confirmed by reading `spektrafilm.c`'s `_resolve_stock`: darktable's "auto" paper-follow only has two tiers — the film's own `target_print` if set, else the *first* `stage:"printing"` entry in the whole pack by name, full stop, no filtering by `channel_model`/compatibility at all. This produced a real, confirmed bug during testing: `kodak_trix400` shipped with `target_print: null` (no B&W paper existed yet), so darktable paired it with `kodak_2302` — a cine *duplicating negative* intermediate stock (the only `channel_model:"bw"` printing-stage entry that happened to exist), not a real paper, with its own independently-calibrated exposure axis — and the rendered image came out crushed almost to black. Any new film product needs a real paper `target_print` before it's meaningfully testable in darktable; check what `stage:"printing"` stocks actually exist in the pack first (most are color paper — see the `products/` bullet above for the paper-building process).

**The exposure axis isn't independently cross-calibrated between a stock's two source charts, by design, not by oversight.** A Characteristic Curve chart (full-spectrum sensitometer exposure) and a Spectral-Sensitivity chart (monochromator spectrograph exposure) are two different classical measurement conventions that a single manufacturer datasheet doesn't reconcile for you. Every product's `build()` anchors its density-curve family so the representative curve's own "density = base + `log_sensitivity_density_over_min`" crossing lands at the canonical grid's logE=0, and digitizes `log_sensitivity` at its printed absolute values, unmodified — see `kodak_trix400.py`'s own module docstring for the full reasoning. A future product's build script should do the same and print/log the same caveat, not silently assume the two axes already agree.
